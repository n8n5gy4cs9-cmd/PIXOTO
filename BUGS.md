## Category 1: Bugs & Logic Errors

### BUG-001 — Auto-snapshot for drawing tools NEVER fires (HIGH)
**File:** `app.js:1389`
**Description:** The auto-snapshot capture listener checks `Pixoto.toolManager._viewport` (with underscore prefix), but `ToolManager` stores the viewport as `this.viewport` (no underscore, see `tool-manager.js:75`). Because `_viewport` is always `undefined`, the condition on line 1389 is always `false`, and the entire `addEventListener('pointerdown', ...)` block is **never registered**.
**Impact:** Brush, eraser, fill, pixelate-brush, pixelate-rect, and pixel-sort strokes are **never captured in undo history**. Ctrl+Z only works for explicit `saveSnapshot()` calls (crop, add layer, duplicate layer, etc.), not for any drawing operation.
**Why it's a problem:** Undo is the #1 safety net. Without it working for strokes, every misplaced brush mark is permanent unless the user manually reverts.
**Severity:** 🔴 HIGH

---

### BUG-002 — `performCropToSelection()` missing `_sizeCanvases()` call (HIGH)
**File:** `app.js:1155-1162`
**Description:** `performCropToSelection()` manually sets `engine.display.width/height` and `engine.uiCanvas.width/height` but does **not** call `engine._sizeCanvases(w, h)`. This means the CSS `style.width`/`style.height` on the display canvas, UI canvas, and wrapper element are never updated.
**Impact:** After crop-to-selection, `getBoundingClientRect()` returns stale dimensions, causing `screenToCanvas()` to compute wrong coordinates. All tools (brush, selection, crop, etc.) will draw at incorrect positions — the **exact same bug** that was fixed in `tools/crop.js` but was missed here.
**Why it's a problem:** Crop-to-selection is a core workflow. Coordinates being wrong after it makes the app unusable until refresh.
**Severity:** 🔴 HIGH

---

### BUG-003 — `origPointerDown` variable assigned but never used (LOW)
**File:** `app.js:1387`

**Impact:** Dead code. Confusing for future maintainers — suggests incomplete implementation.
**Why it's a problem:** Zombie variable. No runtime impact but signals unfinished work.
**Severity:** 🟡 LOW (zombie code)

### BUG-004 — `file-manager.js` deserialize uses stale `activeLayerIndex` (MEDIUM)
**File:** `file-manager.js:237-242`
**Description:** `_deserializeProject()` sets `engine.layers.length = 0` to clear all layers, then calls `engine.addLayer()` in a loop. But `addLayer()` inserts at `this.activeLayerIndex + 1`. After clearing layers, `activeLayerIndex` still holds its previous value (could be any index), so the first `addLayer()` call uses a stale index for `splice()`.
**Impact:** When `activeLayerIndex` was > 0 before load, layers may be inserted at wrong indices. `splice(staleIndex + 1, 0, layer)` on an empty array silently creates sparse entries or misorders layers.
**Why it's a problem:** Loading a saved project could produce a corrupted layer stack. This is intermittent — only happens when `activeLayerIndex > 0` before load.
**Severity:** 🟠 MEDIUM

---

### BUG-005 — Color picker `getBoundingClientRect()` returns 0 when modal hidden (MEDIUM)
**File:** `ui/color-picker.js` (cursor positioning in `_updateAll`)
**Description:** When `setColor()` is called while the color picker modal is not visible (e.g. during initialization or from eyedropper), `getBoundingClientRect()` on the picker canvas returns `{width: 0, height: 0}`. This means the cursor/thumb positions are calculated as `NaN` or `0`, placing them incorrectly.
**Impact:** On first open of the picker after a color change, the cursor and hue/alpha thumbs may be in the wrong position until the user interacts.
**Why it's a problem:** Visual glitch that makes the color picker look broken on first open.
**Severity:** 🟠 MEDIUM

## Category 4: Touch & Mobile Risks

### TOUCH-001 — Layer drag reorder uses HTML5 Drag API (MEDIUM)
**File:** `ui/layers-panel.js:144-170`
**Description:** Layer reorder uses `dragstart`, `dragover`, `drop` events. HTML5 Drag and Drop API does **not** fire on mobile touch — it requires mouse events. On mobile, users cannot reorder layers by dragging.
**Why it's a problem:** Layer reorder is a core editing feature. Mobile users have no way to change layer order.
**Severity:** 🟠 MEDIUM

---

### TOUCH-002 — `touch-action: none` not set in `index.html` on canvas element (LOW)
**File:** `index.html` (canvas elements)
**Description:** `touch-action: none` is set in `style.css` on the viewport wrapper (confirmed at lines 667, 1389, 1417, 1782, 1802), but it's applied via CSS class, not inline. If CSS fails to load or a specificity conflict overrides it, the canvas could fall back to browser gesture handling.
**Why it's a problem:** Low risk, but the CSS-only approach means any specificity override could re-enable browser pan/zoom gestures on the canvas.
**Severity:** 🟢 LOW

## Category 5: PWA & Offline Risks

### PWA-001 — No iOS Safari Blob download fallback (MEDIUM)
**File:** `file-manager.js` (export flow)
**Description:** `exportImage()` uses `URL.createObjectURL()` + programmatic `<a>` click for download. On iOS Safari (both browser and PWA), programmatic `<a>` clicks for blob URLs are sometimes blocked or silently fail. There's no `navigator.share()` fallback for iOS.
**Why it's a problem:** Export may silently fail on the most common mobile platform for PWAs.
**Severity:** 🟠 MEDIUM

---

### PWA-002 — Service worker cache list may be incomplete (LOW)
**File:** `sw.js:10-25`
**Description:** `ASSETS_TO_CACHE` is a hardcoded list. If new files are added to the project (e.g. new tool files, icon assets), they must be manually added to this list or they won't be available offline.
**Why it's a problem:** Forgetting to add a new file to the SW cache list breaks offline mode silently.
**Severity:** 🟡 LOW

## Category 6: Render Mode Consistency

### RENDER-001 — Eyedropper samples composited display, not raw layer (LOW)
**File:** `tools/eyedropper.js:48`
**Description:** `getPixel(x, y, true)` reads from the composited display canvas. This means the sampled color reflects blending mode, opacity, and layer stacking — not the actual pixel data on the active layer.
**Why it's a problem:** If a user has a red pixel on the active layer but a blue layer below with 50% opacity, the eyedropper picks up the blended purple, not the red. This is arguably correct ("sample what you see") but differs from Photoshop's "Current Layer" mode.
**Severity:** 🟢 LOW (design decision, not a bug — but worth documenting)

---

### RENDER-002 — `pixelate.js` uses `layer.canvas.width` instead of `engine.docWidth` (LOW)
**File:** `tools/pixelate.js:329-330` (`_applyPixelSort` method)
**Description:** `w = Math.min(w, layer.canvas.width - x)` uses `layer.canvas.width` for bounds. After crop operations, `layer.canvas.width` should match `engine.docWidth`, but if a layer wasn't properly resized during crop, this could produce out-of-bounds reads.
**Why it's a problem:** Using `layer.canvas.width` is fragile — it depends on crop correctly resizing all layers. Using `engine.docWidth` would be more defensive.
**Severity:** 🟢 LOW

## Category 7: State & Memory

### MEM-001 — Color picker registers 6 document-level listeners, never removes them (MEDIUM)
**File:** `ui/color-picker.js:114-145`
**Description:** `_wireEvents()` registers 3× `document.addEventListener('pointermove', ...)` and 3× `document.addEventListener('pointerup', ...)` (for area, hue, and alpha pickers). These anonymous arrow functions are **never removed** — no `removeEventListener()` exists anywhere in the file.
**Impact:** These listeners fire on **every** pointermove event globally, even when the color picker is closed. On mobile, this means 3 extra function calls per touch-move frame, checking boolean flags and returning immediately. Not catastrophic but wasteful.
**Why it's a problem:** Memory leak pattern. If the picker were ever destroyed/recreated, old listeners would accumulate. Current implementation is a singleton so it's bounded, but it's still poor practice.
**Severity:** 🟠 MEDIUM

---

### MEM-002 — `onLayerChange`/`onActiveLayerChange` callbacks are overwritten, not chained (MEDIUM)
**File:** `ui/layers-panel.js:33-34`
**Description:** `this.engine.onLayerChange = () => this.render()` and `this.engine.onActiveLayerChange = (idx) => this._onActiveChanged(idx)` directly overwrite these callback properties. Any previously set callback (e.g. from history manager, file manager, or other UI components) is silently lost.
**Impact:** Only the last component to set these callbacks will receive notifications. If history.js or file-manager.js also needs to listen, they won't get called.
**Why it's a problem:** This is a single-subscriber pattern. As the app grows, it will break when multiple systems need layer change notifications.
**Severity:** 🟠 MEDIUM

---

### MEM-003 — Flood fill stack can consume excessive memory on large canvases (LOW)
**File:** `pixel-engine.js:870-885`
**Description:** The contiguous flood fill pushes 4 `[x, y]` array entries per visited pixel. For a uniform-color canvas of 4000×4000 = 16M pixels, this creates up to 64M array entries in the stack before completion. Each entry is a 2-element array (16 bytes minimum in V8), totaling ~1GB of heap.
**Impact:** On very large canvases with large uniform areas, flood fill can freeze the tab or cause an OOM crash.
**Why it's a problem:** The classic scanline fill optimization would reduce stack size dramatically but is not implemented.
**Severity:** 🟡 LOW (only affects very large canvases with large uniform fills)
